# Инструкции для агентов разработки

Этот файл действует для всего репозитория `home-project-control`. Пользователя зовут Дмитрий. Ассистент использует имя Ильич, когда говорит о себе.

## Основной принцип

- Оперируй только фактами из репозитория, результатов проверок и явно подтверждённых требований.
- Не выдавай предположение, рекомендацию или внешний ориентир за подтверждённый факт.
- Разделяй тип утверждения, происхождение доказательства и статус проверки по общей онтологии.
- Не публикуй, не выполняй `git push`, не создавай pull request или release и не обновляй установленную копию плагина без отдельного подтверждения Дмитрия.
- Не меняй вручную внешние каталоги плагинов, пользовательские настройки Codex или Claude Code и marketplace вне репозитория.

## Перед началом работы

1. Прочитай `README.md`, `DEVELOPMENT.md` и относящиеся к задаче файлы.
2. Проверь `git status --short --branch` и не затрагивай посторонние изменения пользователя.
3. Определи меняемый слой: manifest, общая онтология, структура проекта, скилл, Python-утилита, тест или документация.
4. Перед изменением скилла полностью прочитай его `SKILL.md` и только необходимые связанные ресурсы.
5. Если требование допускает существенно разные трактовки, запроси решение Дмитрия до изменения поведения.

## Карта репозитория

- `.agents/plugins/marketplace.json` — локальный marketplace с одной записью `home-project-control`.
- `.claude-plugin/marketplace.json` — marketplace Claude Code с той же записью.
- `plugins/home-project-control/.codex-plugin/plugin.json` — manifest плагина.
- `plugins/home-project-control/.claude-plugin/plugin.json` — manifest Claude Code того же плагина.
- `plugins/home-project-control/schemas/ontology.json` — канонические сущности, измерения, связи и инварианты.
- `plugins/home-project-control/schemas/project-structure.json` — каноническая структура пользовательского проекта.
- `plugins/home-project-control/references/` — общие протоколы папки, чтения и онтологии.
- `plugins/home-project-control/skills/` — 15 скиллов; имя папки совпадает с `name` во frontmatter.
- `tests/test_project_tools.py` — поведенческие тесты проектных утилит.
- `tests/test_schema_consistency.py` — согласованность онтологии, реестров, миграций и состава скиллов.
- `.github/workflows/validate.yml` — JSON, Python и тесты.

## Инварианты продукта

- Плагин устанавливается один раз; каждый пользовательский проект находится в отдельной папке вне исходников плагина.
- До профильной работы `inspect_project.py` должен подтвердить текущую папку и вернуть `existing_project_ready`, `gate_passed: true`.
- Оригиналы проектных документов не изменяются.
- Создание, восстановление и миграция выполняются после показа плана и подтверждения пользователя.
- MCP, HTML-формы, визуальная часть и файл `Установить Контроль дома.cmd` не входят в текущую архитектуру.
- Утверждённая базовая линия не смешивается с коммерческими предложениями.
- Принятая управленческая база отдельно и версионируемо связывает одну готовую смету и один готовый календарный план для одного состава работ; изменение не переписывает её автоматически.
- Физический прогресс, договорное выполнение, приёмка, платёж и эксплуатационная готовность не объединяются в один статус.
- Перед первым анализом КП база принимается владельцем отдельным `OwnerDecision` и фиксируется версионным `BaselineSnapshot`; без неё справочное сопоставление не выдаётся за проверку соответствия базе.
- Анализ КП независимо фиксирует текущие `AsIsSnapshot` и `BaselineSnapshot`, классифицирует каждый факт и каждое требование выбранного контекста и не смешивает конфликт факта, проекта и предложения.
- Каждый вариант КП получает единое сравнение, нормализованную цену, структурированные уточнения и сценарий стоимости и срока; договорная готовность предпочтительного варианта требует готовых `CostPlan` и `SchedulePlan`.
- Итоговая рекомендация по КП проходит отдельную оппонирующую проверку; недостаточность доказательств не скрывается итоговым вердиктом.
- Физический объект, зона, система, конкретный индивидуально учтённый `Asset` — хранящийся или установленный — и кандидат на покупку `EquipmentOption` остаются разными сущностями.
- История обслуживания, отказов, ремонтов, модернизаций и замен дописывается и не очищается автоматическим структурным восстановлением.
- Возраст оборудования сам по себе не является основанием замены; рекомендация и решение владельца хранятся раздельно.
- Отсутствие записи о скрытой трассе не подтверждает её отсутствие и не разрешает вмешательство.
- Полное чтение подтверждается только для точной версии документа завершённым `ReadingRun` без пробелов покрытия.
- Полное физическое чтение и полное смысловое извлечение различаются: для второго нужен завершённый `FactExtractionRun` той же точной версии.
- Один оригинал документа хранится один раз; факты связываются с несколькими дисциплинами, пакетами, зонами и системами без копирования источника.
- `InformationGap` блокирует только явно перечисленные зависимые выводы; независимый анализ продолжается.
- Пакеты до комплексного решения проверяются на общие ресурсы, интерфейсы и коллизии через `CoordinationRun`.
- Резюме ЛПР и полное досье используют один канонический структурированный блок, а не два независимых пересказа.
- При анализе КП обязателен актуальный поиск альтернативных подрядчиков с источниками и проверкой сопоставимости.
- Нормативный результат и фактическая практика хранятся раздельно.
- Статус нормативного документа, его применимость к объекту и результат соответствия являются разными измерениями; одно не доказывает другое.
- Мониторинг официальных нормативных источников только сигнализирует об изменении и не принимает новую редакцию, не меняет применимость и не переписывает прежнюю оценку автоматически.
- Проектные данные, секреты, архивы и сгенерированные пакеты не добавляются в репозиторий.

## Правила изменений

### Manifest и marketplace

- Сохраняй имя `home-project-control` одинаковым в папке, обоих manifest и обоих marketplace.
- Не добавляй ссылки на отсутствующие companion-файлы.
- Не меняй версию или cachebuster только ради локального обновления; штатный helper и переустановка требуют отдельного подтверждения.

### Онтология и структура

- Не объединяй `statement_kind`, `evidence_origin` и `verification_status` в одно поле.
- Синхронизируй изменения `ontology.json` со скиллами, документацией и аудитом.
- Синхронизируй `project-structure.json` с `init_project.py`, `inspect_project.py`, `repair_project.py`, потребителями и тестами.
- Несовместимое изменение требует новой версии структуры и безопасной миграции с предварительным просмотром и резервной копией.
- Не создавать подтверждённые площадки, системы или установленное оборудование автоматически из прежних свободных полей паспорта либо вариантов закупки.

### Скиллы и утилиты

- Сохраняй корректный YAML frontmatter с `name` и `description`.
- Не дублируй большие общие протоколы в каждом `SKILL.md`; используй общие references.
- Записывающая утилита ограничивает целевой путь, сохраняет существующие данные и поддерживает предварительный просмотр, когда применимо.
- Не меняй форматы JSON, JSONL или CSV без обновления всех потребителей и документации миграции.
- Не пропускай строку документа из-за низкой суммы; глубину внешней проверки можно распределять по материальности и риску.

## Проверки перед передачей результата

```powershell
Get-ChildItem -Recurse -File -Filter *.json | ForEach-Object {
    Get-Content -LiteralPath $_.FullName -Raw | ConvertFrom-Json | Out-Null
}
python -m compileall -q plugins/home-project-control/skills
python -m unittest discover -s tests -v
```

Если доступны системные скиллы Codex, дополнительно запусти validator плагина и `quick_validate.py` для каждой папки скилла. Если доступен Claude Code, запусти `claude plugin validate . --strict`. На Windows используй UTF-8 mode для русскоязычных файлов.

В итоговом сообщении укажи изменённые файлы, проверки, непроверенные участки и отсутствие публикации.
