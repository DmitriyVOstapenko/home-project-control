# Разработка «Контроля дома»

Документ описывает состояние рабочего дерева после перехода к архитектуре без MCP и визуальных форм 18 августа 2026 года.

## Текущее состояние

- Репозиторий содержит один плагин `home-project-control` с отдельными marketplace и manifest для Codex и Claude Code.
- В плагине 14 скиллов и 14 Python-утилит; инвентаризация PDF, таблиц, DOCX и изображений использует доступные в среде профильные Python-модули и явно блокируется при их отсутствии.
- Оба manifest подключают общий каталог `./skills/`; продуктовая логика не дублируется по средам.
- Общая онтология хранится в `schemas/ontology.json`.
- Машинный обязательный минимум анализа КП хранится в `schemas/proposal-review-contract.json`; версия `1.4` требует доказательную нормативную оценку для завершённого нормативного пункта и не ограничивает дополнительные проверки модели.
- Эталон пользовательской структуры версии `7.0` хранится в `schemas/project-structure.json`.
- Общая онтология версии `5.0` отделяет нормативный документ, атомарное требование, область применимости, оценку и результат соответствия.
- MCP-сервер, `.mcp.json`, три HTML-формы и PowerShell-обёртка удалены из архитектуры.
- Файл `Установить Контроль дома.cmd` не является частью продукта или процесса распространения.
- Базовые версии manifest Codex и Claude Code синхронизируются; Codex дополнительно использует cachebuster сборки.
- Плагин подготовлен для установки из публичного GitHub marketplace в Codex и Claude Code; публикация в централизованных каталогах каждой среды остаётся отдельным процессом их проверки.
- GitHub Release не создаётся автоматически при коммите или pull request; это отдельное действие владельца репозитория.
- Текущий предмет плагина — строительство, ремонт, покупка и эксплуатация физических объектов, а также жизненный цикл установленного на них оборудования. Проект может включать несколько связанных площадок. Универсальное управление произвольными нефизическими проектами в предмет не входит.

## Пользовательский маршрут

1. Плагин устанавливается один раз в Codex или Claude Code из GitHub marketplace либо из клонированного репозитория.
2. Пользователь открывает отдельную папку конкретного проекта.
3. `inspect_project.py` проверяет карточку, привязку пути, каталоги и форматы реестров только на чтение.
4. `init_project.py --dry-run` показывает создание нового проекта; запись выполняется после подтверждения.
5. `repair_project.py` показывает восстановление или миграцию; `--apply` применяется после подтверждения и резервирует заменяемые служебные файлы.
6. Прикреплённые и внешние документы классифицируются по описанию пользователя; `ingest_documents.py` сначала показывает план, а с `--apply` копирует их в тематические папки без изменения источника.
7. Принятые документы индексируются, независимо инвентаризируются с `DocumentInventory`, читаются по версиям с `ReadingRun`, конспектируются и проходят отдельный `FactExtractionRun`.
8. Факты связываются с дисциплинами и `ProjectPackage`; неизвестные данные регистрируются как `InformationGap` с перечнем зависимых выводов.
9. Перед первым КП владелец принимает точный набор полностью прочитанных версий; `record_baseline_snapshot.py` атомарно фиксирует `OwnerDecision`, факты, требования и `BaselineSnapshot`.
10. До комплексного решения пакеты проверяются на общие ресурсы, потребности, интерфейсы и коллизии через `CoordinationRun`.
11. Для регулируемых решений `check-regulatory-compliance` проверяет официальный статус документа, извлекает атомарные пункты и отдельно фиксирует применимость и соответствие с доказательствами и границей специалиста.
12. Любое КП проходит универсальный `ProposalReview`: одно или несколько профессиональных направлений, пакет проекта, базовый режим, двустороннее покрытие либо справочное сопоставление, расчёты, технические проверки, нормативная оценка и воспроизводимый внешний поиск.
13. Машинный контракт требует закрыть все универсальные пункты, каждую профильную ось, четыре направления технических альтернатив и прорабские разделы. После этого модель отдельно записывает полезные проверки сверх обязательного минимума в `additional_model_checks`.
14. Карточка ЛПР и полное досье получают один и тот же канонический блок решения из валидированной записи.

## Модель данных

Три измерения утверждения независимы:

- `statement_kind` — факт, наблюдение, расчёт, интерпретация, гипотеза, норма, рекомендация или неизвестное;
- `evidence_origin` — владелец, утверждённый проект, КП, фактический документ либо тип внешнего источника;
- `verification_status` — состояние проверки.

Базовая линия хранится в `approved_requirements.jsonl`; предложения — в `quotes.jsonl` и `quote_items.jsonl`. Формальная связь показывает точное, частичное, конфликтующее, отсутствующее, лишнее или непроверяемое соответствие. Полная схема сущностей и инварианты находятся в `schemas/ontology.json`.

Состав обязательного анализа КП версионируется отдельно в `schemas/proposal-review-contract.json`. Версия `1.0` поддерживается только при аудите истории; новые записи используют текущую версию. Статусы `completed`, `not_applicable`, `blocked` и `requires_specialist` не скрывают невозможность проверки. `ready_for_owner` разрешён только при точном манифесте и без незакрытых обязательных пунктов. Открытый массив `additional_model_checks` сохраняет выводы, которые текущая или будущая модель обнаружила сверх фиксированного минимума.

Физическая модель разделяет площадку (`Site`), зону (`Zone`), конструктивный элемент (`PhysicalElement`), инженерную систему (`System`) и конкретный индивидуально учтённый физический экземпляр (`Asset`). `Asset` регистрируется с подтверждённого приобретения, приёмки или иного индивидуального учёта и может храниться либо быть смонтирован. До появления такого экземпляра продукт или вариант остаётся `EquipmentOption`, `Alternative`, `Comparable` либо предметом предложения; приобретение, хранение, монтаж и ввод фиксируются раздельно. События эксплуатации дописываются в историю; аналитическая рекомендация о ремонте или замене не является решением владельца.

Нормативный слой разделяет `NormReference`, атомарный `RegulatoryRequirement`, границы `ComplianceAssessment`, отдельный результат `ComplianceResult` и технический журнал `RegulatorySyncRun`. Действующий статус документа не доказывает его применимость, а применимость не доказывает соответствие. Изменение отпечатка официальной страницы создаёт только сигнал для содержательной проверки.

Структура `2.0` добавила журналы чтения и коммерческого анализа, `3.0` — физический объект и жизненный цикл оборудования, `4.0` — независимую инвентаризацию и центральный `ProposalReview`, `5.0` — версионируемую базовую линию, `6.0` — пакеты проекта, смысловое извлечение фактов, формальные пробелы данных, общие ресурсы и межпакетную координацию. Структура `7.0` добавляет нормативные требования, оценки, результаты и журналы синхронизации. Существующие документы, JSONL и операционные CSV сохраняются; добавочная миграция поддерживает проекты `1.0`–`6.0`. Старые полные `NormReference` сохраняются как исторические, но не могут обосновывать новый `ComplianceAssessment` без актуальной карточки статуса и применимости.

| `record_regulatory_assessment.py` | Проверка и атомарная запись нормативных источников, требований, оценок и результатов | Только с `--apply` |
| `check_regulatory_updates.py` | Проверка отпечатков официальных нормативных страниц и отчёт о сигналах изменений | Состояние только с `--write-state` |
| `build_proposal_dossier.py` | Карточка владельца, запрос подрядчику и полное досье | Только с `--apply` |

## Проверки

Минимальный локальный набор:

```powershell
Get-ChildItem -Recurse -File -Filter *.json | ForEach-Object {
    Get-Content -LiteralPath $_.FullName -Raw | ConvertFrom-Json | Out-Null
}
python -m compileall -q plugins/home-project-control/skills
python -m unittest discover -s tests -v
```

Дополнительно:

```text
plugin-creator/scripts/validate_plugin.py plugins/home-project-control
skill-creator/scripts/quick_validate.py <каждая папка в plugins/home-project-control/skills>
```

На Windows для русскоязычных `SKILL.md` валидатор с системным Python запускать в UTF-8 mode: `python -X utf8`.

## Правила изменения схем

- Изменение сущности или допустимого статуса синхронно отражать в `ontology.json`, документации, создаваемых реестрах, аудите и потребляющих скиллах.
- Изменение структуры синхронно отражать в `project-structure.json`, `init_project.py`, `inspect_project.py`, `repair_project.py` и тестах.
- При несовместимом изменении повышать `structure_version` и обеспечивать предварительно просматриваемую миграцию с резервной копией.
- Не выводить `Asset` автоматически из старого поля паспорта или `EquipmentOption`: идентичность физического экземпляра, площадка, приобретение и факт монтажа требуют отдельных подтверждений.
- Историю обслуживания, отказов, ремонтов и замен не очищать автоматическим структурным восстановлением.
- Не использовать размер строки как основание не читать или не регистрировать её; приоритет внешней проверки может зависеть от суммы и риска.

## Установка разработанной версии

Изменение файлов репозитория не обновляет установленную копию автоматически. Обновление cachebuster, переустановка плагина, commit, push, pull request, release и публикация выполняются только после отдельного подтверждения Дмитрия.
