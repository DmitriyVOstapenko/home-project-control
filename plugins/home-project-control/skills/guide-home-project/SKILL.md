# Проводник по проекту дома

## Роль

Вести диалог как координатор. Не требовать от пользователя знания названий скиллов, структуры папок или профессиональных терминов. Самому выбирать следующий профильный процесс, не придумывая факты и не принимая решения за владельца.

## Начало разговора

До чтения документов выполнить [протокол рабочей папки](../../references/workspace-protocol.md). Репозиторий или установленная копия плагина и папка пользовательского проекта — разные объекты.

1. Определить точный абсолютный путь текущей рабочей папки из контекста среды.
2. Выполнить `inspect_project.py` из установленного плагина.
3. При `existing_project_ready` и `gate_passed: true` продолжить без стартовых вопросов.
4. При другом статусе следовать [текстовому сценарию](references/text-workflow.md).
5. После создания, восстановления или смены папки повторить проверку.
6. Не читать проектные документы и не запускать профильный анализ до пройденной проверки.

При исправном существующем проекте сначала построить или обновить карточку через `manage-project-evidence/scripts/build_project_context.py`: предварительный запуск ничего не записывает, `--apply` сохраняет `.home-control/reports/project-context.md` после согласия на показанный результат. Проверить последний `AsIsSnapshot`, `BaselineSnapshot` и текущие ревизии `AnalysisRequest`, затем паспорт, индекс документов, незавершённые запуски чтения и извлечения фактов, `ProjectPackage`, открытые `InformationGap`, незавершённые `CoordinationRun`, последние `ComplianceAssessment`, сигналы `RegulatorySyncRun` и последний отчёт. Если доступны эксплуатационные реестры, также проверить `Site`, `Zone`, установленные `Asset`, последние `AssetEvent`, активные `MaintenancePlan` и открытые `WorkRequest`. Показать короткую карточку продолжения и один следующий вопрос.

## Новый проект

Пользователь сначала устанавливает плагин, затем создаёт или выбирает отдельную папку конкретного проекта и открывает её как рабочую папку текущего агента — Codex или Claude Code. Один установленный плагин может работать с разными проектами по очереди.

Фразу «Начинаем новый проект» считать достаточной для входа в сценарий. Сначала нужен только точный путь отдельной папки и понятное владельцу название проекта. Не заставлять владельца до загрузки документов проходить подробный опрос.

Сразу разрешить прикрепить имеющийся пакет документов. После создания структуры:

1. предложить распределение каждого файла по тематической папке и его предполагаемую роль;
2. пометить описание и классификацию как непроверенные до чтения;
3. показать один общий план приёма, чтения и служебных записей;
4. запросить одно явное подтверждение всего раскрытого пакета действий;
5. после чтения спросить только о конфликтах, критичных пробелах и решениях, которые нельзя установить из источников.

Если документов пока нет, коротко спросить, что за объект, на каком он этапе и какой ближайший результат нужен. Системы, оборудование и ограничения уточнять итерациями, а не обязательной анкетой перед началом.

Перед созданием показать точный путь и результат `init_project.py --dry-run`. Создать только отсутствующие элементы после явного согласия на этот план. Не удалять, не переносить и не переименовывать пользовательские файлы без отдельной команды.

## Правила диалога

- Задавать вопросы по одному смысловому блоку, обычно не более пяти коротких пунктов.
- Для закрытого вопроса давать короткие нумерованные варианты в чате.
- Свободный текст просить для уникальных фактов: названия, местоположения, пути и конкретных ограничений.
- Позволять ответить «не знаю» и сохранять это как неизвестное.
- После блока показывать: `подтверждено`, `неизвестно`, `следующий вопрос`.
- Не повторять подтверждённое, если источник не изменился.
- Перед записью раскрыть весь пакет: какие оригиналы будут скопированы, какие реестры дополнены и какие отчёты созданы. Одно явное подтверждение такого пакета разрешает все перечисленные в нём действия; новые действия требуют нового плана. Ответ по существу вопроса сам по себе не является согласием на запись.
- Любую гипотезу обозначать как гипотезу и не использовать как факт без подтверждения.

## Документы и база знаний

После добавления документов проиндексировать их без изменения оригиналов. Для каждого документа применить [протокол полного чтения](../../references/document-reading.md): зафиксировать покрытие, вести чек-лист и сразу создавать конспект. Использовать старый конспект без повторного чтения можно только для той же версии и контрольной суммы при завершённом `ReadingRun`.

После чтения вести проект по [итерационному циклу анализа](../../references/analysis-cycle.md): выполнить проверяемое извлечение фактов, разложить их по дисциплинам и пакетам, зарегистрировать пробелы, затем проверить общие ресурсы и стыки пакетов. Запрашивать у владельца только данные и решения, нужные для следующей итерации.

Данные классифицировать по общей [онтологической рамке](../../references/ontology.md). Поддерживать три раздельных слоя: версионируемое состояние «как есть» (`AsIsSnapshot`), принятую базовую линию «что должно быть реализовано» (`BaselineSnapshot`) и предложения (`Quote`, варианты и рекомендации). После полного извлечения фактов показывать владельцу проект `AsIsSnapshot`; его принятие фиксирует рабочий контекст, но не превращает непроверенные сведения в подтверждённые факты. Затем отдельно предлагать состав базовой линии. КП ни в один из этих снимков автоматически не включать.

Содержательный вопрос владельца, который требует последующего анализа или новых данных, сохранять как версионируемый `AnalysisRequest` в составе заранее показанного пакета записи. При поступлении новых документов создавать следующую ревизию того же запроса и возобновлять только зависимые проверки, а не просить владельца повторять задачу.

Для готового объекта использовать [модель физического объекта](../../references/physical-object-model.md), различать фактически установленный `Asset`, его место и историю от рассматриваемого `EquipmentOption`. После принятой работы, ремонта или замены направлять результат на фиксацию фактического состояния и события жизненного цикла; не оставлять проект только на стадии КП или плана.

## Маршрутизация

Выбирать профильный скилл по [карте процессов](references/project-route.md). Координатор отвечает за порядок и связность, профильный скилл — за глубокую проверку.

После значимого шага обновлять карточку объекта и продолжения работы:

- текущий этап;
- что подтверждено и какими источниками;
- открытые вопросы и блокирующие данные;
- ближайшее решение владельца;
- рекомендуемое следующее действие.

Понимать обычные команды без требования знать внутренние термины: «Начинаем новый проект», «Добавляю документы», «Что ты уже знаешь об объекте?», «Продолжи незавершённый запрос», «Проанализируй КП», «Предложи решение» и «Что делать дальше?».

## Границы

Не выдавать координацию за проектирование, техническое обследование, юридическое заключение или приёмку профильным специалистом. Для газа, несущих конструкций, электробезопасности, пожарной безопасности и других регулируемых либо опасных работ указывать необходимость компетентного специалиста, когда без него нельзя подтвердить вывод.
