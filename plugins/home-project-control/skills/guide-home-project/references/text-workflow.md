# Текстовый сценарий начала проекта

## Существующий проект

Выполнить входную проверку по [workspace-protocol.md](../../../references/workspace-protocol.md). Если проект готов, построить предварительную карточку `build_project_context.py`, проверить текущие `AsIsSnapshot`, `BaselineSnapshot` и последние ревизии `AnalysisRequest`, затем паспорт, индекс документов, незавершённые `ReadingRun` и последний отчёт. Если существуют эксплуатационные реестры, также проверить `Site`, `Zone`, установленные `Asset`, последние `AssetEvent`, активные `MaintenancePlan` и открытые `WorkRequest`. Затем кратко показать подтверждённое состояние, неизвестное, незавершённые запросы и один следующий вопрос.

## Новый проект

После фразы «Начинаем новый проект» запросить точный путь отдельной папки и название. Если к сообщению уже прикреплены документы, не задерживать их приём подробной анкетой. Если документов нет, спросить одним коротким блоком только вид объекта, текущий этап и ближайший результат.

После подтверждения точного пути выполнить предварительный просмотр `init_project.py --dry-run`, показать результат и отдельно запросить согласие на создание отсутствующих элементов. После создания повторить `inspect_project.py`.

Затем принять пакет документов по одному общему manifest `ingest_documents.py --manifest`: показать `файл → тематическая папка`, описание, совпадения и все планируемые служебные записи. Одно подтверждение распространяется на весь раскрытый пакет. После чтения задать только вопросы, необходимые для разрешения конфликтов, закрытия критичных пробелов или фиксации решения владельца.

## Неполная или старая структура

Показать статус и точный перечень отсутствующих или неверных элементов. `repair_project.py` сначала запускать без `--apply`. Применение создаёт недостающее, резервирует заменяемые повреждённые служебные файлы и обновляет версию структуры; оно допустимо только после согласия пользователя на показанный план.

Конфликт привязки пути, чужую карточку проекта или небезопасную папку автоматически не исправлять.

## После запуска

До профильного анализа проиндексировать добавленные документы. Для каждого документа определить, требуется ли полное чтение, повторное чтение новой версии или можно использовать ранее завершённый конспект с совпадающей контрольной суммой.

После смыслового извлечения предложить владельцу отдельно принять снимок состояния «как есть», затем отдельно — базовую линию «что принято сделать». Зарегистрировать незавершённый содержательный запрос как `AnalysisRequest` и показывать его в карточке продолжения.

Далее выбрать маршрут по ближайшей задаче: формирование паспорта, строительство или ремонт, эксплуатационное вмешательство, обслуживание, решение о замене, выбор оборудования, запрос или проверка КП. Для готового объекта не начинать с полного строительного опросника, если ближайшая задача локальна и необходимые локации и активы уже подтверждены.
