# Обязательный контракт анализа КП

Машинный источник состава контракта — `schemas/proposal-review-contract.json`. Текущая версия `1.4` дополнительно требует доказательную нормативную проверку по атомарным требованиям, когда пункт `norms_and_specialist_boundary` завершён. Версии `1.0`–`1.3` распознаются только для аудита уже записанной истории; новая запись должна использовать текущую версию. Контракт задаёт минимальный результат, но не ограничивает дополнительные способности модели.

## Обязательные слои

1. `mandatory_checks` закрывает каждый универсальный `check_id` из контракта ровно один раз.
2. `discipline_checks` закрывает каждую обязательную ось для каждого значения `disciplines`. Для нестандартного направления применяются те же оси.
3. `technical_alternative_assessments` отдельно исследует улучшение предложенного решения, вариант того же класса, иной технический принцип и вариант продолжения эксплуатации, ремонта, отсрочки либо отказа от вмешательства.
4. Прорабские разделы фиксируют границы объёма и ответственности, мысленный проход исполнения, полную денежную экспозицию, проверку подрядчика, план проверки на объекте, план приёмки, приоритетные риски и итоговый вердикт.
5. `additional_model_checks` содержит любые дополнительные вопросы, риски, расчёты и варианты, которые модель обнаружила сверх минимума. Массив может быть пустым только после явной попытки дополнительного анализа; выполненная попытка кратко фиксируется в `additional_analysis_summary`.
6. Завершённый `norms_and_specialist_boundary` ссылается хотя бы на один завершённый `ComplianceAssessment`; статус `not_applicable` вместо этого содержит доказанное основание неприменимости. Название нормативного документа без точного пункта и результата не закрывает слой.

## Статусы

- `completed` — проверка выполнена; обязательны результат, источники и содержательные наблюдения с локаторами и статусами проверки.
- `not_applicable` — пункт неприменим; обязательны результат, конкретное объяснение, доказательство неприменимости и источники.
- `blocked` — выполнить нельзя; обязательны результат, причина и точный список недостающих данных.
- `requires_specialist` — нужен профильный расчёт или заключение; обязательны результат, граница требуемой проверки и точный список исходных данных.

`ready_for_owner` допускает в обязательных слоях только `completed` и `not_applicable`. `blocked` и `requires_specialist` сохраняются в промежуточном досье, но блокируют готовность к решению.

Отсутствие принятой базы не является универсальным `blocked`: оно фиксируется в `baseline_limitations` и блокирует только зависимые выводы. `ready_for_contract` требует `accepted_baseline`.

Универсальные проверки перечислены в `non_waivable_universal_check_ids`: они применимы к любому КП и не закрываются статусом `not_applicable`. Если документ не содержит расчёта, гарантии или иной ожидаемой части, проверка всё равно выполняется и фиксирует отсутствие либо непроверяемость.

## Техническая альтернатива

Для выполненного направления фиксировать решение, применимость к конкретному проекту, преимущества, ограничения, влияние на монтаж и смежные системы, стоимость жизненного цикла, основание производительности, цены и реализуемости, рекомендацию, источники и связанные `Alternative`. Не подменять другой технический принцип другим подрядчиком той же системы. Разные направления должны ссылаться на разные фактические варианты; повтор допустим только с явным доказательным объяснением.

Если вариант неприменим, не выдумывать его ради формы: поставить `not_applicable` и доказательно объяснить причину. Формулировки «не требуется» или «альтернатив нет» без анализа не закрывают пункт.

## Манифест

`completion_manifest` содержит версию контракта и точные списки записанных обязательных пунктов, комбинаций `discipline|axis`, направлений технических альтернатив, дополнительных проверок, блоков объёма, фаз исполнения, осей проверки подрядчика, проверок на объекте, пунктов приёмки и приоритетных рисков. Манифест не заменяет результаты; он позволяет машине проверить полноту.
