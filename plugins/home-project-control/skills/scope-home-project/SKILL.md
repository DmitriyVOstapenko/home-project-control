# Паспорт и состав работ

## Входной контроль проекта

До чтения документов выполнить [протокол рабочей папки](../../references/workspace-protocol.md). Продолжать только при `existing_project_ready` и `gate_passed: true`; иначе передать создание или восстановление проводнику. Каждый анализируемый документ читать по точной версии с [контролем покрытия](../../references/document-reading.md), а утверждения классифицировать по [общей онтологии](../../references/ontology.md). Не формировать паспорт до пройденной проверки; при смене папки проверить её заново.

Для готового объекта, нескольких площадок и установленного оборудования использовать [модель физического объекта](../../references/physical-object-model.md).

## Интерактивные вопросы

Задавать вопросы в чате небольшими блоками. Для закрытых вопросов давать короткие нумерованные варианты; свободный текст оставлять для уникальных фактов. Ответ не заменяет отдельного согласия на запись или внешнее действие.

## Основной порядок

1. Определить локальную папку проекта. Не считать текущую рабочую папку папкой проекта без подтверждения пользователя.
2. Если структура проекта ещё не создана, предложить использовать `manage-project-evidence/scripts/init_project.py`. Создавать её только после согласия пользователя.
3. Задавать вопросы последовательно, по одному смысловому блоку. Не требовать заполнить весь опросник одним сообщением.
4. Сначала определить этап жизненного цикла, иерархию объектов и локаций и исходное состояние, затем инженерные системы, установленное оборудование, работы, эксплуатационные, бюджетные и временные ограничения.
5. Для каждого пункта использовать один статус: `нужно`, `возможно`, `не нужно`, `уже есть — проверить`, `неизвестно`.
6. Записывать только ответы пользователя и факты из указанных документов. Не превращать типичное решение в требование конкретного проекта.
7. После каждого блока показывать краткое резюме и следующий открытый вопрос.
8. По завершении сохранить согласованный паспорт в `.home-control/project.json` и человекочитаемую версию в `00_Паспорт_проекта/Паспорт проекта.md`.

Для каждой системы со статусом `нужно`, `возможно` или `уже есть — проверить` дополнительно выяснить: желаемый результат, текущее состояние, исходные документы, обязательные параметры, связи с другими системами, ограничения монтажа, способ проверки результата, эксплуатацию и обслуживание. Не задавать эти вопросы для исключённых блоков.

Для готового объекта определить, одна ли это локация или несколько, и зафиксировать доступную иерархию до помещения или зоны карты. Установленное оборудование описывать как фактический `Asset` только при подтверждённой связи с местом и источником. Рассматриваемую модель сохранять как `EquipmentOption`, не как установленный актив. Детальную историю обслуживания, ремонта и замены передавать в `operate-property-and-equipment`.

Сохранять незавершённость опроса: какие блоки пройдены, какой вопрос открыт и когда обновлено. При возобновлении продолжать с первого незакрытого блока, а не начинать заново.

## Классификация сведений

Для каждого утверждения независимо указывать `statement_kind`, `evidence_origin` и `verification_status` из общей онтологии. Прямой ответ владельца имеет происхождение `owner_confirmation`; утверждение документа сохраняет конкретный документ и локатор; согласованное предположение остаётся `agreed_assumption`, а неизвестное — `unknown`.

Если документ противоречит словам пользователя, зафиксировать обе записи и статус `conflicted`, не выбирая победившую версию самостоятельно. Не превращать подтверждение релевантности внешнего источника в утверждённое проектное требование без отдельного решения.

## Формат диалога

Использовать компактные чек-листы:

```markdown
- [ ] Нужно
- [ ] Возможно
- [ ] Не нужно
- [ ] Уже есть — проверить
- [ ] Неизвестно
```

В обычном чате пользователь может отвечать словами или номерами; не требовать интерактивную форму. Полный перечень блоков читать из [systems-checklist.md](references/systems-checklist.md).

## Результат

- краткое описание объекта и его исходного состояния;
- перечень подтверждённых локаций, систем и установленных активов либо пробелов инвентаризации;
- перечень нужных и исключённых систем и работ;
- ограничения и приоритеты;
- перечень уже имеющихся документов;
- открытые вопросы, риски и необходимые обследования;
- согласованный следующий шаг.

Отдельно сформировать `готово к планированию`, `нужно обследование`, `нужно проектирование`, `нужно решение владельца` и `отложено`. Не смешивать желаемую функцию с выбранным техническим решением.

Не выдавать проектные решения по газу, несущим конструкциям, электробезопасности, пожарной безопасности или другим регулируемым системам за подтверждённые без проекта либо заключения профильного специалиста.
